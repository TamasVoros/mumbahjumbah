# Use Cloudflare Workers + Hono + D1 for v1, not Next.js + Postgres + Vercel

**Status:** accepted

The design doc's Cross-Model Perspective hinted at `@vercel/og`/`satori` for Recap Card generation, which implied Next.js on Vercel, but no stack was ever actually chosen — this repo had no scaffolding at all. We considered Next.js + Postgres + Vercel (the doc's implicit hint) but chose **Cloudflare Workers + Hono + D1** instead, because the user already runs other side projects on Cloudflare's free tier and wants to consolidate hosting rather than add a second platform/billing relationship for a validation-stage project. D1 (serverless SQLite, 500MB free tier) is comfortably enough for v1's single-Operator, low-write-volume data model — there is no need for Postgres's extra capability at this scale. Hono is the idiomatic lightweight router for Workers, serving both the API and server-rendered HTML (grid form, leaderboard, organizer controls) from one Worker, with no separate frontend framework needed for v1's simple pages.

The Recap Card PNG generation still works on this stack: `satori` + `@resvg/resvg-wasm` is the same rendering engine `@vercel/og` wraps, and runs on Workers without Node-specific APIs — the doc's rendering approach survives the platform switch unchanged.

**Deliberate deviation from D1's own suggested pattern:** Cloudflare's D1 documentation recommends one database per tenant/entity for multi-tenant apps, not a single shared database with a tenant-id column. We chose the shared-database pattern anyway (one D1 database, every table scoped by a real `operator_id` foreign key) because Approach C (the cross-team jargon index) needs to aggregate across many Operators' data — trivial with one shared database, painful with Cloudflare's per-tenant-database sharding (would require fanning a query across many separate SQLite files, or replicating into a separate analytics store). Per-tenant-DB sharding is Cloudflare's advice for isolation at massive scale (thousands of tenants); this project's realistic ceiling (the business model's own target: ~50 paying facilitators) never approaches D1's free-tier 500MB limit on a single shared database. A future engineer should not "fix" this into per-Operator databases without re-solving cross-Operator aggregation first.

**Consequence:** if a future phase needs capabilities D1 genuinely doesn't have (heavy concurrent writes, complex joins at scale well beyond the above), migrating off D1 is a real cost — acceptable to defer given v1/v2's actual scale, revisit only if usage materially exceeds the facilitator-tier ceiling the business model itself targets.
